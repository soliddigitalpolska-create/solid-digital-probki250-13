Odtworzenie sprawdzone.
Regresja wykonana.

Natywny WordPress 7.1.3 i WooCommerce 11.2.1, odizolowana kopia własnego sklepu. Kopia bazy i plików, celowa awaria, odtworzenie oraz test koszyka, dostawy i zamówienia BACS.

To techniczna demonstracja własna, bez płatnej realizacji. Regułę błędnie blokującą połączenie odtworzono we własnej wtyczce. Działający endpoint jest kontrolowanym serwerem lokalnym, nie usługą WordPress.com. Nie diagnozowano rzeczywistego sklepu klienta ani jego hostingu.
01

Kopia → awaria → odtworzenie

Prawdziwy ZIP bazy SQLite i własnych plików. Następny proces PHP potwierdził celową zmianę, a po przywróceniu — pierwotne wartości i bajty pliku.

02

Wąska reguła HTTP

Przed zmianą natywne WP HTTP API blokowało żądanie. Po zmianie dotarło do lokalnego serwera. Inne hosty i niezatwierdzona ścieżka pozostały zablokowane.

03

Regresja WooCommerce

Produkt fizyczny i usługa trafiły do natywnego koszyka. Woo wyliczyło dostawę i utworzyło zamówienie BACS. Osobny proces odczytał trwały wynik.

Precyzyjny zakres dowodu

Wywołano natywne API PHP WordPressa i WooCommerce. Nie wykonano przeglądarkowego checkoutu, aktualizacji wersji ani pomiaru przyspieszenia. BACS jest lokalnym testem przelewu ręcznego — nie pobrano pieniędzy, nie wywołano rzeczywistego operatora płatności i nie wysłano poczty.

Poprzednie źródła i baza pozostały identyczne. Wszystkie zmiany dotyczą nowej kopii v2. Potwierdzenie konkretnej usterki WordPress.com, warunków hostingu i zakresu prac wymaga oddzielnego wstępnego sprawdzenia rzeczywistego środowiska.
