Workflow 01

CSV → CRM przez API

Dwa poprawne kontakty zapisano w lokalnym API CRM. Test wymusił kolejno HTTP 429 i 503; trzecia próba zakończyła się sukcesem. Błędny kontakt odrzucono, trwała awaria trafiła do kolejki dead-letter. Po ponownym otwarciu zapisów dwa kontakty pominięto jako już przetworzone.

Workflow 02

Zamówienie → akceptacja → dokument

Dwa poprawne zamówienia zapisano do kolejki, błędną ilość odrzucono. Przed jawną decyzją testową nie istniał żaden dokument. Po akceptacji Z1 powstał rzeczywisty dokument HTML oraz jeden rekord outbox. Powtórzona akceptacja nie utworzyła drugiego rekordu. Z2 nadal czeka.

Workflow 03

Webhook → weryfikacja → raport

Trzy zgłoszenia przyjęto przez prawdziwy lokalny endpoint HTTP. Jawne reguły przypisały kategorie billing/support/manual. Przed decyzją testową nie powstało żadne zadanie. Dwie akceptacje utworzyły dwa zadania, odrzucenie pozostawiło ślad. Wygenerowano rzeczywisty raport CSV; wejście zaczynające się od znaku = zostało zneutralizowane dla arkusza.

Co zabezpieczają testy

  • Transport klienta API dopuszcza wyłącznie dokładny adres uruchomionego lokalnego serwera oraz listę endpointów. Inne adresy i przekierowania są blokowane.
  • Kontrolowane HTTP 429 i 503 wywołują ponowienie, a trwale nieudany rekord trafia do dead-letter zamiast otrzymać fałszywy status sukcesu.
  • Ponowne uruchomienie oraz powtórzone webhooki i akceptacje nie mnożą rekordów.
  • Endpointy zadań i outbox sprawdzają zapisane zatwierdzenie. Odrzucają próbę pominięcia etapu weryfikacji.
  • Raport CSV neutralizuje formułę w danych wejściowych; dokument HTML koduje treść.
Decyzje zatwierdzenia w pokazanym teście podano jawnie parametrem --approve-demo. To symulacja wejścia recenzenta służąca sprawdzeniu bramki, nie deklaracja ręcznej oceny danych klienta. Klasyfikator zgłoszeń korzysta z przejrzystych reguł; nie uruchomiono LLM ani płatnego API. Outbox zapisuje dokumenty, ale nie ma transportu SMTP.

Odtworzenie

Python 3.13 i biblioteka standardowa. Nie potrzeba kluczy, płatnych usług ani instalacji zależności. Uruchom w nowym pustym katalogu wynikowym; lokalny port jest wybierany automatycznie.

python -m unittest discover -s sources -p test_workflows.py -v
python sources/run_demo.py --approve-demo --output local-demo-new

Po zakończeniu lokalny serwer jest zamykany, a osobny interpreter odczytuje bazę. Sam publiczny pakiet nie zawiera bazy, kont ani sekretów. Kod jest przykładem skryptowym Python/API; nie przedstawiamy go jako natywnego workflow n8n lub Make.

Zakres produkcyjnego wdrożenia ustala się po poznaniu procesu, systemów, API, limitów i odpowiedzialności za decyzje. Dowody dotyczą dokładnie tych trzech lokalnych scenariuszy.
